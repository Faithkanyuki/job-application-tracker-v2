# Technical Write-Up: Job Application Tracker

## Overview

This is a standalone job application tracker built with Next.js App Router, TypeScript, PostgreSQL, Drizzle ORM, Better Auth, and Tailwind CSS. Users sign up, save jobs they're interested in, and track each one's progress through a status pipeline (Saved → Applied → Interview → Offer → Rejected), with private notes attached. Every piece of data is scoped to the logged-in user and enforced server-side.

## Architecture

The application is a single Next.js 16 project using the App Router, which means the frontend and backend live in one codebase rather than as separate services. Routing is filesystem-based: `app/dashboard/[id]/page.tsx` is both the file location and the actual URL structure, with `[id]` capturing a dynamic segment.

Two kinds of components are used deliberately. Most of the UI is built as **Client Components** (`"use client"`), since the app is heavily interactive — forms, live status updates, session-aware navigation — and needs `useState`/`useEffect` running in the browser. The **API layer** (`app/api/*/route.ts`) runs entirely server-side, using Next.js Route Handlers, which serve the same purpose a separate Express backend would, but colocated in the same project.

Data flows in one direction, consistently: a client component calls `fetch()` against one of the app's own API routes; that route authenticates the request, validates input, queries the database through Drizzle, and returns JSON. The client never talks to the database directly, and no page fetches data through anything other than the app's own authenticated API — this keeps the authorization boundary in exactly one place rather than scattered across the codebase.

Route protection for `/dashboard/*` is handled by `proxy.ts` at the project root (Next.js 16's naming for what was previously `middleware.ts`), which performs a fast existence check on the session cookie before any dashboard HTML is even rendered. This is a UX-layer safeguard, not the real security boundary — that distinction matters and is covered under Authorization below.

## Authentication

Authentication is handled by Better Auth, which manages password hashing, session token generation, and cookie handling internally — no password or token logic was written by hand. Three sign-in methods are supported: email/password, Google OAuth, and GitHub OAuth, all configured in `lib/auth.ts`.

Sessions are stored in an **HttpOnly, SameSite=Lax cookie**, deliberately not in `localStorage`. This means client-side JavaScript — including any injected via an XSS vulnerability — cannot read the session token directly, which is a meaningfully stronger default than a common pattern of storing tokens in browser storage.

Server-side, every protected API route calls `getCurrentSession()` (`lib/getSession.ts`), which asks Better Auth to verify the session cookie against the database on every single request. This is intentionally more expensive than trusting the cookie's mere presence, and intentionally separate from the `proxy.ts` check — the proxy stops obviously-unauthenticated page loads early for a better user experience, while the API layer is where authentication is actually enforced.

**A notable real-world nuance surfaced during development:** Better Auth supports linking multiple sign-in methods (e.g. email/password and Google) to a single account, but only auto-links when the existing account's email is marked `emailVerified: true`. An account created via the plain email/password form starts as unverified, since this project doesn't implement an email-confirmation flow — so its first attempt to link an OAuth provider on the same email is deliberately blocked, to prevent a scenario where an attacker could claim an unverified email and "link" a real OAuth account to it. This is documented in the README as a known, understood trade-off rather than treated as a bug.

## Database

PostgreSQL (hosted on Neon) is the persistence layer, accessed through Drizzle ORM for both schema definition and querying. The schema has three logical groups of tables:

- **Better Auth's own tables** (`user`, `session`, `account`, `verification`) — generated by Better Auth's CLI and owned by it, not hand-written.
- **`jobs`** — one row per role a user is tracking: title, company, location, URL, description, owned by `userId`.
- **`applications`** — one row per tracked application, linked to a job via a `UNIQUE` foreign key on `jobId`.

The `jobs`/`applications` split is deliberate: a job is information about a role that exists independently of whether the user is tracking it yet, while an application represents the user's actual progress. Modeling them as separate tables with a one-to-one relationship (enforced by the database itself, via the `UNIQUE` constraint) rather than one merged table keeps that distinction real rather than conceptual — the database physically rejects a second application for the same job, regardless of what the application code does.

Every foreign key uses `onDelete: "cascade"`. Deleting a user removes their jobs and applications automatically; deleting a job removes its linked application automatically. No manual cleanup code is needed to avoid orphaned rows — that guarantee comes from the schema itself, not from remembering to write the right delete logic every time.

Schema changes are managed through `drizzle-kit generate` (reads the TypeScript schema, writes a versioned SQL migration file) and `drizzle-kit migrate` (applies pending migrations to the actual database). Migration files are committed to the repository, so the database's structure has the same version history as the application code.

## Authorization

Authentication answers "who is this," authorization answers "what are they allowed to touch" — and the second question is enforced independently on every single request, not inferred from the first.

Every job/application route handler follows the same pattern: authenticate, fetch the specific record by ID, then explicitly compare the record's `userId` against the authenticated session's user ID, before allowing any read, update, or delete. Creating an application goes one step further, checking ownership of the *linked job* as well — a user can't create an application for a job they don't own, even if they know its ID.

A deliberate detail: a record that doesn't exist and a record that exists but belongs to someone else both return the identical `404 Not Found`, with identical messaging. If a "not yours" case returned a different error (say, `403 Forbidden`) than a "doesn't exist" case, an attacker could use that difference to enumerate valid IDs belonging to other users, without ever actually accessing their data. Treating both cases identically closes that information leak.

## Lessons Learned

**Authorization needs to be re-checked on every request, not assumed from session presence.** Having a valid session proves who someone is — it says nothing about which specific records they're allowed to touch. The pattern of "fetch, then compare ownership, then act" had to be applied consistently across every single route handler, rather than written once and trusted everywhere.

**Framework and library upgrades surface pre-existing issues, not just new ones.** During a related migration on an earlier version of this project, running a full production build for the first time (rather than only `next dev`) surfaced a Drizzle ORM type error that had nothing to do with the framework upgrade itself — it had simply never been caught before, because the project had never been fully type-checked in build mode. The lesson: a clean `dev` server is not proof a project actually compiles correctly.

**Security defaults sometimes create friction that looks like a bug but isn't.** The `emailVerified`/account-linking behavior initially looked like broken OAuth. Understanding *why* Better Auth blocks the link (an unverified email is an easy thing to fake-claim) turned a confusing error into a deliberate, explainable design decision — and a good example of why reading the actual error and its documentation matters more than immediately working around it.

**A consistent request/response pattern pays off across a whole codebase.** Every route handler in this project follows the same shape: authenticate → validate with Zod → check ownership → act → `try/catch` with a generic client-facing error message. Once that pattern was established on the first route, writing every subsequent one was mechanical rather than a fresh design decision each time — and it made the codebase predictable to review and extend.
